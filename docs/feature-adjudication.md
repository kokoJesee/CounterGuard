# 特征对账分歧的仲裁流程

对账不同只说明两个产物不一致，不能自动证明 benchmark 或提取器正确。任何 mismatch/error 都先阻断 fit；当前 learner 没有“忽略差异”或“人工决议直接放行”的参数。

## 谁负责

- 执行者复现差异、整理源码和规范依据，可以提出原因与修复。
- 数据维护者确认契约、架构元数据和人工标注的来源。
- 项目负责人（用户或其明确指定的人）负责度量标准和冻结标注变更的最终决定；应由没有编写争议实现/标注的审核者复核。执行方不能仅凭自己实现的输出批准真值变更。
- 已有明确授权可以执行对应修正；没有授权的冻结标准变更先形成完整、可审查的新版本，再提交审核，不以一句抽象确认替代审查。

## 决策顺序

1. **先留痕**：保留完整 mismatch JSON、missing/unexpected、metadata_diff、输入 digest、context digest 和失败命令。audit 将每次报告追加到 `artifacts/audits/history/<digest>.json`，保存数据的规范 JSON 快照以及成功提取目标/契约的原始字节快照；最新输出只是指针式副本，不删除旧争议。
2. **独立复核**：以声明的 token 规范、原始源码 AST、业务契约和 module context 来源为依据。不要以“哪一侧能让模型达到预期分数”为依据，也不要在仲裁时调整 Baseline 或读取 holdout 的适用性标签来调规则。
3. **分类**：提取器实现错误、标注错误、规范歧义、两侧都有错误、尚无法确认。无法确认时保持阻断，不能挑一侧作为默认真值。
4. **若提取器错误**：先添加独立正/反例，再按原规范修复代码；标注保持不变。记录代码修订与旧/新 audit digest，用新 artifact root 保存修正结果。若 token 含义或支持边界改变，升级提取器/词汇及相应协议版本。
5. **若标注错误**：先写仲裁记录及正确值的独立理由，再准备数据修订。未冻结数据可在审核后修改并重新冻结；已冻结 scope_v1 的数据、预期计数和报告保留，在新的协议/数据版本修正，并披露旧结果受影响范围。不得修改旧标注后继续宣称同一冻结评测通过。
6. **若规范歧义或两侧错误**：先决定并记录新规范和版本，再分别修正实现与标注，保留两份差异及审核理由。不得同时改两侧只留下一个全绿报告。
7. **最后再放行**：重新独立核对全部样本、运行 feature/context audit、来源审核和相应新协议验收。只有新的 gate 全通过才能拟合；仲裁记录本身不能覆盖 gate 的失败。

## 仲裁记录最低字段

记录存入 `docs/adjudications/<decision-id>.md` 或同等受版本控制的 JSON，至少包含：争议 ID、受影响协议/样本、原 audit digest、源码/契约/context 的引用与摘要、expected/actual、独立规范依据、原因分类、提议者、复核者、决定人、决定时间、旧/新版本、代码/数据差异、新 audit digest、受影响结果范围、最终处置。

有失败/无法解析的源码时，也要在修改前另存其原始字节或对应不可变 Git 修订；只有成功提取的来源会由 audit 自动归档。未完成独立复核或缺少来源证据的争议保持 unresolved。

当前 15 个样本没有实际特征争议；本轮新增流程和保留机制，不制造或自动批准仲裁结论。
